# CPU、GPU 与并行执行模型

## 1. 为什么 GPU 适合大量相似工作

CPU 通常用少量复杂核心处理低延迟任务和复杂分支；GPU 用大量执行单元并行处理相似任务。GPU 的优势不意味着任何程序放到 GPU 都会更快：数据搬运、kernel 启动、可用并行度和同步成本都可能抵消计算收益。

可以把小规模加法作为对照：CPU 直接处理已有的数据，而 GPU 调用还包含 launch 和可能的数据拷贝。工作量、数据位置和后续计算共同决定能否受益，具体时间应在目标机器上测量。

## 2. SIMD 与 SIMT 的直观区别

- SIMD：一条指令对多个数据元素执行同一种操作。
- SIMT：程序员描述许多逻辑线程，硬件把线程组织成组执行。

CUDA 常用术语是 thread、warp、block、grid。其他平台名称和约束可能不同；学习时应先掌握“很多独立索引处理很多元素”这个共性，再学具体 API。

## 3. 用索引推导线程工作

对于长度 N 的向量：

```text
global_id = block_id * threads_per_block + thread_id
```

假设每个 block 4 个线程、N=10：

| block | thread | global_id | 是否有效 |
|---:|---:|---:|---|
| 0 | 0 | 0 | 是 |
| 0 | 3 | 3 | 是 |
| 1 | 0 | 4 | 是 |
| 2 | 1 | 9 | 是 |
| 2 | 2 | 10 | 否，必须屏蔽 |

对于二维输出矩阵，通常用二维 grid 映射 row/col，再用 `row * stride + col` 得到地址。映射方案是算法设计，不是硬件自动猜出来的。

## 4. Block、SM 与同步范围

CUDA block 是调度和协作的常见单位。一个 block 在一个 SM 上执行；同一 block 的线程可通过 shared memory 协作，并用 `__syncthreads()` 建立 block 内屏障。普通 kernel 没有通用的 grid 级屏障，因此跨 block reduction 通常需要第二次 kernel、原子操作或专门的 cooperative launch 机制。

不要把 warp 宽度、SM 数量或每 SM 资源写死在跨平台代码里。运行时查询和平台文档才是依据。

## 5. 分支和发散

若同一 warp 的线程走不同分支，硬件可能需要分别执行多个路径。尾块中的 `if (idx < N)` 通常是必要边界保护，不能为了消除分支而冒险越界。要区分“分支存在”和“分支是瓶颈”；只有 profiling 表明控制流显著影响性能时才优化。

## 6. 小练习

1. 对 N=37、block=16，计算 grid 大小和无效线程数。
2. 对矩阵 M=5、N=7，列出 row-major 中 `A[3,2]` 的线性偏移。
3. 解释为什么不同 block 不能用普通 `__syncthreads()` 同步。
4. 解释为什么将 CUDA warp=32 的假设直接移植到其他 GPU 风险很大。

## 7. thread、warp、block、SM：哪些是代码组织，哪些是硬件

把一个程序设为 100 个 block，每个 block 256 个线程，并不意味着机器同时拥有 25600 个独占的物理计算核心。thread 是携带索引和局部状态的逻辑执行实例；block 把可协作的线程组织起来；SM 是实际调度、发射和执行这些工作的硬件单元。

在 CUDA 的执行模型中，block 内线程被组织成 warp。一个 SM 可驻留多个 block/warp，数量取决于线程、寄存器、共享内存等限制；剩余 block 等待资源空出。blockIdx 是工作编号，不是 SM 编号，也不能用 blockIdx 假定两个 block 同时启动或按编号顺序执行。

假设只有一个 block，那么即使它有很多线程，也不能自动让所有 SM 都分担这个 block 的普通计算。因此前面的单 block Reduce 是理解协作的起点，但大规模输入可能需要多个 block 分段归约。反过来，block 越多也不保证更快，因为启动、尾块和每块工作量都要考虑。

## 8. 一个线程等待内存时，其他线程怎样帮助它

假设 warp A 发起 global load，数据尚未返回，后面的乘法又依赖该值；这时 A 暂时不能继续执行这条依赖链。若同一 SM 还有就绪的 warp B，调度器可发射 B 的指令，让执行单元继续工作。这就是用独立工作掩盖等待的直觉。

要使这件事成立，至少要有其他驻留且就绪的工作。增加线程数不一定制造独立性：所有 warp 可能同时等待相同类型的资源，或者单线程寄存器过多使可驻留 warp 变少。

occupancy 通常描述活跃 warp 相对于硬件上限的比例，反映“能有多少工作驻留”，不直接等于“执行单元忙碌程度”。高 occupancy 的 kernel 仍可能访问不合并、同步频繁；低 occupancy 的 kernel 也可能凭借充分的指令级并行和数据复用获得较好速度。它是诊断线索，不是优化目标的唯一分数。

## 9. 一次 kernel 调用的宿主/设备时间线

~~~text
CPU: 准备参数 → 提交 kernel → 继续执行后续 CPU 工作 → 等待结果
GPU:                排队 → 执行 kernel → 完成
~~~

普通 launch 往往先让宿主继续运行，不能在 launch 后立即用一个宿主秒表时间差断言“GPU 算完了”。如果随后发生同步或把结果复制回宿主，等待时间可能出现在那个位置。

因此读 profile 时要区分“谁提交工作”“谁执行工作”“谁等待工作”。看到某个同步 API 耗时很长，可能只是前面的 GPU 工作尚未结束，不代表同步函数本身进行大量计算。调试和计时需要有意选择同步点，而不是把同步加在每一个算子后面。

## 10. 并行算法的三种依赖关系

Vector Add 的 y[i] 只依赖 a[i]/b[i]，因此不同 i 独立。Reduce 的一个输出依赖许多输入，需要局部聚合再合并。GEMM 的不同输出独立，但这些输出重复使用很多输入，适合让线程协作搬运并复用数据。

这三种关系决定了不同的并行化策略。拿到一个新算子时，先画出“某个输出需要哪些输入”，再决定线程分配；不要先选 block=256，再去猜数学公式怎样塞进去。

例如 Softmax 的 y[i] 既依赖 x[i]，又依赖整行的最大值和分母；它的最后一步是逐元素，但前面必须有归约。LayerNorm 同样具有先统计再广播的依赖。理解它们是组合结构，才能从已学过的 Vector Add/Reduce 迁移。

## 11. 同步与竞争的最小反例

假设两个线程都执行 counter=counter+1，counter 初值为 0。这个表达式可分成读取、加一、写回。若两者都先读到 0，再各自写入 1，最终 counter=1 而不是 2。即使结果偶尔为 2，也不能证明没有竞争。

atomicAdd 使针对同一地址的加法按原子语义发生，但不会自动形成整个 grid 的屏障，也不保证浮点加法次序固定。barrier 则让协作线程在某个阶段相遇，解决阶段间依赖；它本身不把多个普通写操作变成原子加法。

练习：线程 A 写 shared[0]，线程 B 读它。若能保证两者都执行同一 block 的屏障，且屏障位于 A 写后、B 读前，就建立了所需阶段顺序。若它们属于不同 block，普通 __syncthreads 不能建立这个关系。

## 12. 阅读 kernel 前的纸面检查

任选一个输出，写下它的所有输入索引；再选末尾一个输出重复这件事。标记哪些值是线程私有，哪些会被别人读取；在共享值的“写完”和“读完”之间放入需要的同步。最后估算有多少独立 block，可以给多少 SM 提供工作。

这里每一步都会直接影响后面代码的正确性或性能。若无法在纸上讲清，先缩小输入和线程数进行模拟，比直接阅读复杂高性能模板更容易定位理解缺口。
