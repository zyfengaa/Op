# 阶段二 · 基线：正确但慢是必经之路

## 这一步在防什么

没有金标准，后面每一次“优化后仍然正确”的判断都是自证。

基线实现的作用不是跑得快，是**定义一个可以反复对照的正确答案**。它慢是设计的一部分——如果基线本身就快，说明你已经在优化了，而优化不该在没有参照的情况下开始。

## 合格判据

**基线故意不求快。** 用最直白的写法：一个线程一个元素，或者一个 Python 循环一次。可读性优先于任何性能考虑。

**期望值必须来自基线。** 优化版本的正确性检查，是拿它的输出和基线输出比。绝不能反过来——不能因为优化版本跑出了某个值，就认为那个值是对的。

**基线自己也要被验证。** 用一个**已知答案**的输入确认基线是对的：手算的小例子、解析解、或者和框架原生实现对照。这一步不做，后面全部建立在沙地上。

## 参考实现放在哪

各算子目录的 `impl/` 下。同一目录里，基线版本和优化版本并列，用文件名区分（`naive_*`、`v1_*`、`v2_*`），这样对比时不会拿错对象。

## 测试怎么设计

### 边界覆盖来自阶段一

阶段一列出的边界输入，逐条变成测试用例：非整除长度、空输入、size-0 维度、单元素、极值、非连续。

一个只覆盖“典型输入”的测试集，会在每个边界上放行一个 bug。

### 手算锚点

至少有几个用例的期望值是**手算出来的常数**，不是从代码里跑出来的。

本仓的故障题库用了这个做法：每个参考答案都配一个手算锚点，判题脚本自检时会核对它们。这类锚点的价值在于——它不依赖任何实现，所以能同时抓住基线和优化版本一起错的情况。

### 覆盖要能击中

一个测试用例只有在**故意写错时确实失败**，才算有效用例。

本仓 `09-practice/check.py selftest` 就是这个思路：它要求每个故意写错的版本至少被一个输入击中。如果某个错误版本能通过全部输入，说明测试集有洞，不是那个错误不存在。

## 常见误区

**先写快版本，再拿它当基准。** 两边一起错，测试全绿。这是最隐蔽的一类失败。

**测试只覆盖整除长度。** 整除通过、末项为零——这个失败模式在本仓出现了不止一次。

**用 base 实现之外的东西当期望值。** 比如直接信框架的输出——那要先确认框架在你的 dtype 和 shape 下确实走了你预期的那条路径。

**以为基线一旦写好就不用再看。** 如果后面发现基线本身有问题，所有基于它的结论都要重做。所以基线的正确性要用独立证据（手算、解析解）钉住。

## 一个具体例子

`row_softmax` 的基线：

~~~python
def stable_softmax(x):
    m = max(x)
    weights = [exp(v - m) for v in x]
    denom = fsum(weights)
    return [w / denom for w in weights]
~~~

要点：

- 减 `m` 是为了数值稳定，不是可选的优化——不做的话大输入会溢出。所以它属于基线，不属于优化。
- `fsum` 而不是 `sum`，因为累加顺序影响结果，基线要用更准的那个。
- 这个基线对 `[inf]` 会返回 `nan` 而不报错。**这不是实现问题，是契约没写清**——回到阶段一补上“含 inf 时的策略”。

基线暴露契约漏洞，是常态，不是失败。
