# 阶段三 · 测量：先建立可比口径

## 这一步在防什么

没有可信数字，后面所有关于“快不快”的讨论都是感觉，而感觉不能回归。

测量的目的不是得到一个数，是得到一个**带完整条件的、可以和别的数比较的**数。

## 计时范围：先说清在测什么

同一个算子，三种常用的计时范围给出的数字可以差很多，因为包含的东西不同。

| 范围 | 包含 | 不包含 | 回答的问题 |
|---|---|---|---|
| **Kernel-only** | 只有设备端 kernel 执行 | 内存分配、host↔device 拷贝、启动开销 | 算法本身多快 |
| **Op-level** | kernel + 分配 + 启动 | 上游数据准备 | 框架里调用一次要多久 |
| **E2E** | 从输入就绪到输出就绪，含拷贝 | 模型构造、分词 | 用户实际感受到多少 |

**规则：只有同一范围内的数字才能互相比较。** 拿 kernel-only 的旧数据去比 op-level 的新实现，差异里混进了范围差，结论无效。

数字旁边必须写清范围。本仓的报告里，模型切片的计时明确写了“输入/参数已就绪，包含输出分配和 cache 拼接”。

## Warmup：为什么必须有

第一次调用通常显著慢于后续调用，原因至少三个：

- 惰性初始化：库的句柄、上下文、内核模块在首次调用时才加载。
- 自动调优：部分库在首次调用时选择算法或 tile 尺寸。
- 缓存预热：数据和指令缓存为空。

做法：先空跑若干次不计入，再开始采样。本仓的 benchmark 用 20 次 warmup、100 次采样。

## 采样与统计

**报中位数和区间，不报最小值。** 最小值回答的是“最好情况下能多快”，不是“通常多快”，而且它对测量噪声最敏感。

**多次采样，分组平均。** 单次测量的抖动可能比你要测的优化幅度还大。本仓的做法是多批次、每批多次，对每批的平均值再取统计。

**保留原始样本。** 只留汇总数字，事后无法判断异常值从哪来。

## 输入驻留位置

这一项经常被漏掉，但它直接改变结论：

- 输入**本来就在设备上**（resident）——测的是算子的纯计算成本。
- 每次从 host **传进去再传出来**——测的是端到端成本，包含 PCIe/NVLink 传输。

同一个 kernel，这两种口径下的排名可能反转。报告里必须写清是哪一种。

## 该记录什么

一份可复现的测量至少包含：

~~~text
设备与驱动版本
编译器与编译 flags
dtype、layout
shape（输入输出的完整形状）
线程数 / grid 配置
计时范围（上面三种里的哪一种）
warmup 次数、采样批次数、每批次数
统计量：中位数、最小/最大值
输入驻留位置
源码版本（git 哈希）+ 是否 dirty
~~~

最后一条容易被忽略：源码带哈希，"dirty=true" 说明采集时代码尚未提交。没有这个，报告过一阵就对不上实现了。

## 常见误区

**拿一次运行的单个数字下结论。** 尤其不要拿最小值。

**用不同计时范围比较两个实现。** 这是最隐蔽的误判来源。

**把 profiler 插桩后的时间当普通运行时间。** 插桩本身有开销，可能比被测对象还大。本仓模型报告里，单次插桩的 RoPE 占了 1130.1 us，比不带 profiler 的整块中位数还高——这个数字说明的是插桩开销，不是 RoPE 变慢了。

**一边跑 benchmark 一边开 profiler。** 两者互相污染。

**同时跑多个 benchmark。** 资源竞争会让所有数字失真。

**结果不好看就重测到好看。** 这是选择偏差，不是测量。

## 一个检查清单

- [ ] 计时范围明确写出
- [ ] 有 warmup，且次数记录在案
- [ ] 采样批次和每批次数明确
- [ ] 报的是中位数和区间
- [ ] 输入驻留位置明确
- [ ] 原始样本已保存
- [ ] 源码哈希和 dirty 状态已记录
- [ ] 同一结论只用同一范围内的数字支撑
