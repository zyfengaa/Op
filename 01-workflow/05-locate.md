# 阶段五 · 定位：从证据到瓶颈类型

这是“profiling 之后的分析”真正发生的地方。这一步的产物是一句话：**瓶颈是什么类型**。

分三步走。缺任何一步，结论都是猜的。

## 第一步：算上界

先算清楚这个工作负载**理论上限**在哪，否则你不知道实测数字算好还是差。

~~~text
AI（算术强度） = FLOPs / 搬运字节数
机器平衡点     = 峰值算力 / 峰值带宽        （单位：FLOPs per byte）
Roofline 上界  = min(峰值算力, AI × 峰值带宽)
~~~

AI 低于平衡点 → 内存受限；高于平衡点 → 计算受限。

**搬运字节数要用算法本身需要的量**（读多少、写多少），不是 profiler 计数器的实际值。两者的差，正是第二步要看的。

## 第二步：用实测时间反推有效吞吐

~~~text
有效带宽 = 实际搬运字节数 / 时间
有效算力 = 实际 FLOPs / 时间
~~~

对比第一步的上界，得到**利用率**。这一步才让“快”有了参照。

实际搬运字节数取 profiler 的访存计数器（例如 DRAM 读写字节），不要用理论值——理论上该搬多少和实际搬了多少经常差很远，而那个差往往就是问题所在。

## 第三步：判据表

| 观察 | 判据 | 瓶颈类型 | 下一步方向 |
|---|---|---|---|
| 有效带宽 ≪ 峰值 | 低于峰值约 60%，AI 低于平衡点 | **Bandwidth Bound，访存低效** | 查访问模式和合并度 |
| 有效带宽 ≈ 峰值 | 接近峰值 | Bandwidth Bound，**已到设备上限** | 只能减少搬运量，改不动访问模式 |
| 有效算力 ≪ 峰值，AI 高于平衡点 | 计算单元大量空置 | **Compute Bound（发射/依赖）** | 查 ILP、依赖链、指令混合 |
| 有效算力 ≈ 峰值 | 接近峰值 | Compute Bound，**已到设备上限** | 只能减少计算量或用更快的单元 |
| 两者都远低于峰值，occupancy 低 | 并行度不足隐藏延迟 | **Latency Bound** | 提高并行度 |
| 两者都远低于峰值，stall 以 barrier 为主 | 同步开销占比高 | **同步/调度问题** | 减少屏障、改协作方式 |

**注意“已到上限”这一列。** 到达设备上限时，继续在同一个方向优化是徒劳的——要么减少工作量，要么换算法。区分“低效”和“到顶”，比区分“内存”和“计算”同样重要。

## 第四步：看 stall 原因

occupancy 不是目标，它只是隐藏延迟的手段。真正要读的是 warp stall 统计。

| stall 原因 | 含义 | 对应方向 |
|---|---|---|
| `long scoreboard` | 等全局访存返回 | 访存延迟或带宽 |
| `barrier` | 等 `__syncthreads()` | 同步开销、负载不均 |
| `MIO throttle` | shared memory 或特殊函数端口饱和 | 减少 shared 访问或特殊函数 |
| `not selected` / `wait` | 发射器没活干 | 并行度不足 |

一个反直觉但真实的例子：**occupancy 从 75% 降到 50%，kernel 反而更快**。因为降低 occupancy 换来了更高的数据复用和指令级并行。目标是“足以隐藏延迟并持续供给计算单元”，不是“occupancy 越高越好”。

## 例子一：访存低效

`row-softmax`，shape `[4096, 1024]`，fp32：

~~~text
理论搬运 = 读 4096×1024×4 B + 写 4096×1024×4 B = 32 MiB
实测时间 = 200 us
有效带宽 = 32 MiB / 200 us ≈ 167 GB/s
设该卡峰值带宽 = 900 GB/s
利用率   = 167 / 900 ≈ 18.6%
~~~

结论：Bandwidth Bound 且访存低效。可检验的假设是“同一 warp 访问的地址不连续”。带着这个假设进阶段六。

## 例子二：到了上限，别白费力气

同样形状，优化后：

~~~text
有效带宽 = 810 GB/s，峰值 900 GB/s → 利用率 90%
~~~

结论：**已经到顶**。此时再调访存模式、再加向量化，收益都极小。要更快只能**减少搬运量**——比如和上游算子融合，让中间结果不出内存。

这两个例子的分岔点，就是判据表里“低效”和“到顶”的区分。

## 例子三：看起来是计算，其实是延迟

一个 GEMM，AI 算下来高于平衡点，本该是 Compute Bound。但实测有效算力只有峰值的 15%。

继续看：occupancy 只有 12%，stall 主要是 `long scoreboard`。

修正结论：真正的瓶颈是 **Latency Bound**——不是算力不够，是没足够的 warp 去掩盖访存延迟。方向变成提高并行度，而不是优化计算。

**这就是为什么第四步不能省。** 前三步给出候选类型，stall 数据给出裁决。

## 常见误区

**把 occupancy 当目标。** 它不是。

**只算 AI 不看利用率。** AI 告诉你上界在哪，不告诉你离上界多远。

**把“低效”当成“到顶”。** 看到 80% 带宽就说没救了，可能其实还能到 90%。

**把“到顶”当成“低效”。** 反过来浪费时间。

**忽略 stall 数据直接下结论。** 见例子三。
