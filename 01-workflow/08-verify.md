# 阶段八 · 验收：正确性和性能都要过

## 这一步在防什么

优化最容易骗过自己的地方，就是用“跑通了”代替“正确”，用“单次最快”代替“更快”。

验收要产出**两份独立证据**，缺一不可。

## 正确性验收

### 对着基线对拍

期望值来自[阶段二](02-baseline.md)的基线实现，不是来自这一版自己。

### 覆盖阶段一的全部边界

阶段一列出的每条边界，都要有对应用例。典型的漏网之鱼：

- 非整除长度（末块）
- 空输入 / size-0 维度
- 单元素
- 极值（`±inf`、极大极小）
- 非连续 / 非对齐输入
- 超大 shape（索引溢出）

只测“典型输入”的验收，等于没验收优化——优化引入的 bug 几乎都在边界上。

### 容差要和 dtype 匹配

fp32 和 fp16 的容差不该一样。容差写得太松会放过真 bug，太紧会把正常实现判失败。

### 显式排除 NaN 被当成“接近”

这是一个具体的陷阱：

~~~python
# 错误：两边都是 NaN 时，比较结果为 False 还好；
# 但某些写法（如 abs(a-b) < tol 在 a=b=nan 时）行为不合直觉
# 正确做法：先检查有限性，再比数值
if not (math.isfinite(actual) and math.isfinite(expected)):
    return actual == expected        # 只有两者同为 inf/-inf 才算过
return abs(actual - expected) <= atol
~~~

**一条 NaN 悄悄通过，会让上面所有边界测试失去意义。**

### 手算锚点仍然有效

阶段二的手算常数要在这一版上继续核对。它不依赖任何实现，所以能抓住“基线和优化版一起漂移”的情况。

## 性能验收

### 报中位数和区间

沿用[阶段三](03-measure.md)的口径。优化前的区间和优化后的区间都要给出。

### 区间重叠时，结论是“证据不足”

这是最需要纪律的一条。假设：

~~~text
优化前：中位数 1624.7 us，区间 1290.9 – 2002.6
优化后：中位数 1608.3 us，区间 1376.9 – 1876.8
~~~

中位数看着低了 1%，但**区间大幅重叠**。正确结论是：

> 证据不足以证明存在稳定收益。

**不是**“优化了 1%”，也**不是**“优化无效”——是“以当前样本量，分不出差异”。要下结论，要么扩大采样，要么做分项实验隔离变量。

本仓的模型报告就保留了一个这样“不明显”的结果，供练习如何拒绝过度解释。

### 双重验证的意义

一个优化可能“对了但没变快”，也可能“变快了但错了”。两份证据分别指向这两种失败。只看一份，会把另一种放过去。

## 汇总表

| 版本 | 正确性（边界全过？） | 性能中位数 | 区间 | 相对基线 |
|---|---|---|---|---|
| 基线 | ✅ | 200 us | 190 – 215 | — |
| v2 | ✅ | 180 us | 172 – 191 | 区间不重叠，成立 |
| v3 | ✅ | 178 us | 170 – 192 | 与 v2 重叠，收益不成立 |

## 常见误区

**“跑通了没报错”当正确性验收。** 报错只覆盖越界和崩溃，不覆盖静默算错。

**单次最好成绩当性能验收。**

**区间重叠仍宣布收益。**

**只测优化引入的那条路径，不测新引入的尾块分支。** 尾块往往就是新 bug 所在地。

**容差随结果调。** 发现对不上就放宽容差，这是把 bug 变成“通过”。
