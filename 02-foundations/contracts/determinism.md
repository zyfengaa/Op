# 非确定性

同一个算子、同样的输入、同样的代码，两次运行结果可能不同。这一页说明来源，以及怎么控制。

“我的测试昨天过了今天没过”——相当一部分是这一页的内容。

## 来源一：浮点归约顺序

浮点加法不满足结合律（见 [dtype 与精度](dtype-and-precision.md)）。如果归约的顺序在两次运行间不同，结果就不同。

顺序什么时候会变：

- **多块归约**：各块先算部分和，再合并。块的执行完成顺序不定，如果合并用了非确定的方式，结果会变。
- **动态调度**：线程的实际执行顺序由硬件调度器决定。
- **自动调优**：库在首次调用时选择算法，不同选择对应不同顺序。

## 来源二：原子操作的累加顺序

`atomicAdd` 是经典例子。

~~~text
float partial[N];
// N 个线程各自 atomicAdd 到同一个位置
// 到达顺序由硬件决定
// → 每次运行的求和顺序不同 → 结果有微小差异
~~~

这不是 bug，是原子操作的固有性质。要确定性，就得换成**确定顺序的归约**（比如树形归约 + 固定顺序合并），代价通常是性能。

本仓的教学实现里，`atomicAdd` 与两阶段归约的对比就有这一层：两阶段能给出确定的顺序，原子版不能。

## 来源三：并行任务划分

跨流、跨设备、跨进程的并行，完成顺序不确定。

- 多流并行时，多个 kernel 的完成先后不定。
- 分布式训练里的 allreduce 顺序可能不同。
- 多线程 CPU 实现的调度顺序不定。

## 来源四：库的内部实现

- cuDNN/cuBLAS 会按环境或启发式选择算法，不同算法顺序不同。
- `torch.use_deterministic_algorithms(True)` 会强制确定性算法，代价是性能。
- 某些算子**根本没有确定性实现**，此时开启确定性模式会**报错**而不是变慢——这是有意为之，避免你以为自己得到了确定性。

## 怎么控制

| 手段 | 作用 | 代价 |
|---|---|---|
| 固定归约顺序（树形 + 固定合并） | 消除来源一、二 | 可能更慢 |
| 固定算法选择 | 消除来源四 | 可能不是最快的算法 |
| 固定随机种子 | 消除随机初始化差异 | 不解决归约顺序 |
| 单线程/单块运行 | 消除大部分并行不确定 | 极慢，只适合调试 |
| `use_deterministic_algorithms` | 强制确定性 | 性能损失或直接报错 |

**注意**：固定种子**不能**解决归约顺序问题。两者是独立来源，很多人以为设了 seed 就复现了。

## 什么时候必须确定性

- **回归测试**：测试要能稳定地过或不过。
- **调试**：结果每次都变，无法二分定位。
- **对拍**：要和别的实现比对，两边都得确定。
- **合规场景**：某些领域要求结果可复现。

## 什么时候可以放弃确定性

- **纯推理**：用户不关心最后一位的差异。
- **精度足够的场景**：差异远小于容差。
- **性能优先**：原子版或快算法带来的收益大于可复现的价值。

**但要把放弃写下来。** 契约里登记“本算子非确定，差异量级约为 X”，比事后被问“为什么每次不一样”要省事得多。

## 记录方式

在算子契约里加一段：

~~~text
确定性：非确定
来源：多块归约的部分和合并顺序
差异量级：fp32 下相对误差 < 1e-7，随 K 增大
已验证：K=4096 时 10 次运行的最大相对偏差 3.2e-8
~~~

差异量级这一项很重要——它让你能判断某次“测试失败”是确定性抖动的正常范围，还是真的引入了 bug。

## 常见误区

**以为设了随机种子就复现了。** 种子只解决随机数生成，不解决归约顺序。

**把确定性的性能损失当成 bug。** 它是明确权衡。

**在测试里用严格的位相等比较非确定算子。** 应该用容差，且容差要覆盖已知的确定性抖动。

**没登记非确定性。** 三个月后自己也会被“为什么结果会变”困住。
