# 手法 · 融合

**适用瓶颈**：kernel 启动开销占总时间比例高（时间线上一串短 kernel 与空隙），或中间结果往返全局内存——[阶段五](../../01-workflow/05-locate.md)判定为 Bandwidth Bound 且搬运量本身可减少，或启动/调度开销突出。

## 症状

前三条是**观察**，后两条是待验证的**假设**：

- 观察：时间线上相邻小 kernel 之间有明显空隙，launch 次数远多于数据规模所需。
- 观察：同一块中间张量被写一次、又被下一个 kernel 读一次，且两次都不在 cache 中复用。
- 观察：每个 kernel 的有效带宽/算力都远低于峰值，但每个的绝对时间都很短（数微秒量级）。
- 假设：中间张量的「写 + 读」字节在总时间中占比可观（用下面的估法算，不靠感觉）。
- 假设：去掉中间张量后，端到端时间按省下字节 / 峰值带宽下降。

**先估收益上限**，把中间张量的字节数算清楚：

~~~text
省下的字节 = Σ(中间张量元素数 × 元素字节) × 2      （写一次 + 读一次）
收益上限   = 省下的字节 / 峰值带宽

例：中间张量 4096×1024，fp32 = 16 MiB
    写 + 读 = 32 MiB
    峰值带宽 900 GB/s → 上限 ≈ 32 MiB / 900 GB/s ≈ 35.6 us

若被融合的 kernel 合计 < 40 us，收益可观；
若合计 5 ms，则占比 < 1%，与噪声同量级，属于「证据不足」。
~~~

启动开销的摊薄单独估：融合 N 个 kernel 省下 N−1 次启动，收益上限为 `(N−1) × 单次启动时间 / 原总时间`。**单次 kernel 计算时间在 20 us 以下时，启动成本占比才可能显著。**

## 手段

### 1. 垂直融合（生产者—消费者）

上游算子的输出直接喂给下游，中间结果不落全局内存。典型是 **epilogue 融合**：matmul + bias + 激活在一个 kernel 内完成。

~~~text
separate: read A/B → GEMM → write C → read C → +bias → 激活 → write Y
fused:    read A/B → GEMM → +bias → 激活 → write Y
~~~

**成立条件**：

- 上游每个输出 tile 只被一个下游消费一次（1:1 映射）。若下游要跨 tile 归约（如 softmax 的全局 max），不能直接这么融。
- 融合在数学上等价：dtype、舍入顺序、`NaN`/`inf` 语义不变（见 [dtype-and-precision](../../02-foundations/contracts/dtype-and-precision.md)）。
- epilogue 的计算不改变输出 tile 的形状与布局。

### 2. 水平融合（同形状逐元素）

把形状相同的多个逐元素算子合并进一个 kernel，一次读入、算完所有步骤、一次写出。

**成立条件**：

- 参与算子的输入形状与 broadcast 规则一致，dtype 可兼容提升。
- 算子之间没有跨算子的归约依赖（纯逐元素链）。
- 中间结果本来不会被别处复用（见「什么时候不要做」）。

收益 = 省下的每次中间张量「写 + 读」字节 + 摊薄的启动开销。逐元素算子通常 memory bound，垂直与水平融合的收益都直接落在搬运量上。

### 3. 分支 dispatch 保留非融合路径

融合后同一份代码往往只对某类 shape 划算。

**成立条件**：对短 shape 与小 shape 走融合版本，对大 shape 保留未融合版本；两条路径都要有独立的正确性与性能记录。本仓 GEMM 版本阶梯的教训是**一次只引入一个机制**，融合的 dispatch 也应能单独开关，便于消融归因。

## 融合的代价

| 代价 | 机制 | 观察方式 |
|---|---|---|
| 寄存器压力上升 | 多段逻辑同时活跃的变量增多 | 每线程寄存器数上升 |
| occupancy 下降 | shared/寄存器任一成为限制 | achieved occupancy 下降 |
| 错误定位变难 | 一个 kernel 含多段逻辑，故障面扩大 | 二分注释代码才能定位 |
| 复用性下降 | shape 组合增多、dispatch 分支变多 | 维护与测试矩阵变大 |
| 编译时间/代码体积上升 | 模板展开更重 | 编译产物与构建时间 |

**这些代价要和收益一起进决策表，不能只记收益。**

## 什么时候不要做

- **中间结果很小。** 例如读写合计 < 1 MiB、或在总时间中占比 < 5%，收益会被启动/调度噪声淹没。
- **中间结果被多处复用。** 例如 residual 要同时喂给下一个 block 和 skip 连接；融合会强制重算或让语义变化。
- **融合后寄存器 spill。** 查 profiler 的 register spill 计数，非零（尤其持续 > 0）时复用收益常被 spill 抵消，得不偿失。
- **参与融合的算子并行维度不同。** 一个是按行归约、一个是逐元素，强行同 kernel 会引入低效线程映射。
- **改变数值契约。** 融合会改变中间结果的累积精度或舍入点，这属于契约变更，不是单纯的性能改动，必须先确认契约（见 [dtype 与精度](../../02-foundations/contracts/dtype-and-precision.md)）。

## 验证方式

| 指标 | 期望变化 |
|---|---|
| 端到端（或算子级）时间 | 下降（最终判据） |
| kernel 启动次数 | 下降 |
| 全局内存读写字节 | 下降，尤其中间张量那一层 |
| 每线程寄存器数 | 上升（需记录） |
| achieved occupancy | 可能下降 |
| 融合 vs 未融合的数值误差 | 在容差内（见 dtype 契约） |
| 短 shape 与长 shape | 分别验证——融合常在小 shape 赢、大 shape 因资源下降而输 |

**小 shape 赢、大 shape 输**是融合的常见反转。必须把两种 shape 的结果都写进记录，再决定是否加 dispatch 分支。

## 常见误区

**只算「省了一半字节」就当作「快一倍」。** 收益上限要除以峰值带宽，还要叠加 Amdahl——被优化部分占比低时整体提升很小。

**在中间结果要被复用的图上融合。** 导致重算或语义变化，收益为负。

**融合后不重测边界。** 尾块、broadcast、mask 的 bug 几乎都在融合改动里出现。

**把「kernel 数变少」当成收益。** 判据是总时间，不是 launch 计数。

**忽略 occupancy 下降。** 大 shape 上资源压力可能让融合版更慢，却在小 shape 微基准里看不出来。
