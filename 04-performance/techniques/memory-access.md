# 手法 · 访存模式

**适用瓶颈**：有效带宽远低于峰值，且算术强度低（[阶段五](../../01-workflow/05-locate.md)判定为 Bandwidth Bound 且访存低效）。

## 症状

- 有效带宽只有峰值的 20%–40%
- stall 主要是 `long scoreboard`
- 提高线程数收益很小

## 三个手段

### 1. 合并访存（coalescing）

同一 warp 的 32 个线程，访问的地址应当落在尽量少的连续内存段里。

**反例**：一个 warp 处理矩阵的一列。地址间隔是行宽，32 个线程触达 32 个不同的内存段。理想情况是 1 段 128 字节，实际是 32 段。

| 访问模式 | 一次 warp 请求触达的字节 | 有效利用率 |
|---|---|---|
| 连续（合并） | 128 B（1 段） | 100% |
| 步长 32 个 float | 32 × 128 B | 12.5% |

**修法**：让同一个 warp 处理**连续的**元素。如果算法天然要求跨步访问（比如矩阵列方向），用 shared memory 做中转（见第 3 条）。

### 2. 向量化加载

用 `float4` 之类一次加载多个元素，减少指令数并提高单次请求的字节数。

**成立条件**（必须写进注释）：

- 地址 **16 字节对齐**
- 连续维长度是向量宽度（4）的整数倍
- 否则必须走尾块路径

**对齐检查要算，不能假设**：

~~~text
K = 41, fp32 → 每行 164 字节
行首偏移 = row * 164
164 mod 16 = 4
→ 行 0 偏移 0（对齐），行 1 偏移 164（164 mod 16 = 4，不对齐）
→ 从第 4 行起对齐状态周期性变化
~~~

**没有对齐检查的向量化，是一颗定时炸弹**——在小 shape 上恰好对齐时全部通过。

### 3. Layout 变换 / shared memory 中转

当算法的自然访问模式和合并访存冲突时（典型是转置），用 shared memory 把数据重排一次。

~~~text
读：按合并方式读入 shared tile
同步：__syncthreads()
写：按目标顺序从 shared 写出
~~~

**代价**：一次额外的片上往返 + 一次屏障。**收益**：全局访存从 12.5% 利用率升到接近 100%。

**注意 bank conflict**：shared tile 的列跨度若是 32 的整数倍，同一 warp 会全部撞到同一个 bank。

~~~text
tile[32][32]  → 列访问时 bank = t mod 32 → 全部撞 bank 0
tile[32][33]  → bank = t mod 33 → 分散，冲突消除
~~~

**padding 一列**是消除 bank conflict 的标准做法。

## 什么时候不要做

- **已经接近峰值带宽**。先确认利用率，别优化已到顶的（[阶段五](../../01-workflow/05-locate.md)）。
- **算术强度已经很高**。此时瓶颈在计算，改访存无收益。
- **改访存会改变累加顺序**。那属于契约变更，要回到[阶段一](../../01-workflow/01-anatomy.md)。

## 验证方式

| 指标 | 期望 |
|---|---|
| 有效带宽 | 相比改前显著上升 |
| `long scoreboard` stall | 下降 |
| 全局访存请求数 | 下降（向量化的效果） |
| 正确性边界测试 | 全部通过（尤其非整除、非对齐） |

## 常见误区

**先向量化再去想对齐。** 顺序反了，应该先算对齐条件。

**在未合并的访问上做向量化。** 合并是前提，向量化是叠加。

**忘记尾块路径。** 向量化引入的 bug 几乎都在尾块。

**bank conflict 靠猜。** 用 `bank = 地址 / 4 mod 32` 算出来。
