# 手法 · 常驻 kernel

**适用瓶颈**：kernel 启动开销占总时间比例高（小 shape、多次调用、或每次只处理一点点数据）——[阶段五](../../01-workflow/05-locate.md)时间线显示一串短 kernel 及其间的 launch 空隙。

## 症状

前三条是**观察**，后两条是待验证的**假设**：

- 观察：时间线上 kernel 密集且每个都很短，kernel 之间有可辨认的 launch 空隙。
- 观察：单次 kernel 时间与一次 launch 的往返开销同量级（几微秒），甚至更短。
- 观察：decode 逐 token、算子链、小批量推理场景下，每次调用的工作量很小。
- 假设：把多次调用合并成一次常驻执行后，启动开销与重复取权重被摊薄。
- 假设：这些调用之间**没有强制物化到全局内存的依赖**，可以在 kernel 内顺序处理。

**先估上限**：`收益上限 = (省下的启动次数 × 单次启动开销 + 省下的重复搬运字节 / 峰值带宽) / 原总时间`。若单次 kernel 已运行 > 100 us、启动开销 < 5 us，占比低于 5%，直接排除（见 [06-choose](../../01-workflow/06-choose.md) 的 Amdahl 一节）。

## 手段

### 1. 一次启动，kernel 内循环处理多批任务

grid 大小固定为「SM 数 × 每 SM 可驻留 block 数」，kernel 内用循环取任务、处理、取下一个，直到任务耗尽。

**成立条件**：

- 任务之间可独立处理，任务内不需要跨 block 全局同步。
- 有一个可表达的任务划分方式：固定分片、全局原子计数器、或调用方传入的任务表。
- grid 大小按实际驻留能力设，不写成「任务数」；否则退化成普通 kernel。

### 2. 复用片上状态（与 grid-stride loop 的关键区别）

把权重、常量 tile 加载到 shared memory 或寄存器**一次**，在多批任务间复用。

**成立条件**：

- 权重在所有任务间共享，且能放进片上（shared 或寄存器）。
- 权重的加载成本在总时间中可观——这正是它值得常驻的理由。

### 3. 显式任务队列（动态负载均衡）

用全局原子计数器分发任务：`blockId = atomicAdd(&counter, 1)`，处理到计数器超过任务数为止。

**成立条件**：

- 任务粒度足够大，否则原子争用取代启动开销成为新瓶颈。
- 有明确的终止条件与收尾逻辑，避免漏掉最后一批任务。

### 4. 与算子链结合（decode 逐 token / 小 batch）

把多次调用之间的中间状态保持在设备上，避免每次启动和 H2D/D2H 往返。

**成立条件**：

- 中间状态能放进片上或设备内存，且在多次调用间语义一致。
- 算子链的依赖是顺序的，可在 kernel 内按序推进。

### 常驻 kernel 与 grid-stride loop 的区别

| 维度 | grid-stride loop | 常驻 kernel |
|---|---|---|
| 线程复用 | 是（线程按 grid 步进处理多个元素） | 是 |
| 片上状态复用（权重/tile） | 否，每轮重新取 | **是，加载一次反复用** |
| 任务来源 | 由数据规模决定 | 由队列/分片决定，可动态 |
| 启动次数 | 每次调用一次 | 多次调用合并为一次 |
| 设备占用 | 与普通 kernel 相同 | 常占满设备，影响并发 |
| 复杂度 | 低 | 高（队列、同步、收尾） |

**只复用线程、不复用片上数据**的版本是 grid-stride loop，不是常驻 kernel；别把两者混为一谈。

## 代价

| 代价 | 机制 | 后果 |
|---|---|---|
| 占用整个设备 | grid 按 SM 数 × 驻留数设满 | 与同 stream 上其他 kernel 无法并发，串行化 |
| 与其他 stream 并发性下降 | SM 被常驻 kernel 占住 | 推理服务中并发请求数受限 |
| 需要显式任务队列 | 终止条件、负载均衡要自己写 | 死锁/饥饿风险 |
| 小任务可能变慢 | 队列开销 > 省下的启动开销 | 收益为负 |
| 调试与 profiling 更难 | 一个长 kernel 内混杂多批 | 无法按单批定位 |

## 什么时候不要做

- **单次大 batch 调用，启动开销相对计算可忽略。** 例如 kernel 运行 > 100 us、启动 < 5 us 时，收益低于 5%。
- **设备需要同时跑其他 kernel。** 常驻 kernel 独占 SM，会降低请求并发度；多 stream 场景慎用。
- **任务之间有依赖、必须物化中间结果。** 此时常驻反而不如显式多 kernel 清晰。
- **任务粒度太小。** 原子队列的争用会取代启动开销，成为新瓶颈。
- **无法保证终止与收尾正确。** 漏处理最后一批是常见正确性 bug。

## 验证方式

| 指标 | 期望变化 |
|---|---|
| 端到端时间 | 下降（最终判据） |
| kernel 启动次数 | 下降 |
| 时间线空隙 | 减少 |
| 单 kernel 内处理的任务数 | 上升 |
| 各 block 处理任务数分布 | 大致均匀，无长尾 |
| 与其他 kernel 的并发 | 记录（可能下降，需在收益中说明代价） |
| 正确性：批边界、队列耗尽 | 全部通过 |

**若启动次数下降但端到端时间没降**，说明启动开销不是主要成本，回[阶段五](../../01-workflow/05-locate.md)重定位，而不是继续合并调用。

## 常见误区

**把它当成「只要合并启动就一定更快」。** 忽略设备独占与队列开销，可能在并发场景下更慢。

**用 grid-stride loop 冒充常驻 kernel。** 它复用线程，但不复用已加载的权重，省不下重复搬运。

**任务粒度太小。** 原子计数器成为新瓶颈。

**没有终止条件或收尾逻辑。** 漏处理最后一批，正确性先崩。

**在并发服务里用满整个设备。** 请求并发度下降，端到端吞吐反而变差。
