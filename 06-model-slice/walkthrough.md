# 四个通道的模型工作台：把形状与数值连起来

读模型代码时容易出现一种假懂：知道每个缩写，却不知道上一行输出为什么能进入下一行。本节固定一个很小的例子，让维度、地址和语义都有落点。运行：

~~~powershell
python 06-model-slice/inspect_example.py
~~~

它复用 block.py 的真实模型和函数，不另写一份近似模型。只将尺寸缩小为 B=1、前缀 3 token、D=4、heads=2、head_dim=2、MLP hidden=6，dtype=float64。权重由固定 seed 生成；脚本打印中间 Q、旋转前后数值、mask 和最后一个 token 的完整/缓存输出。

## 1. 输入不是“一个向量”，而是一组有角色的轴

输入前缀是三行，每行四个通道：

~~~text
token 0: [1,  2, 3,  4]
token 1: [4,  3, 2,  1]
token 2: [1, -1, 2, -2]
~~~

加上 batch 轴后 shape 为 [1,3,4]。token 轴决定序列位置；通道轴参与归一化和投影。把它们互换，即使元素总数不变，也会改变模型定义。

这里用人为输入，不需要词表 embedding。实验在 block 的入口开始，不声称这些四维数是某种自然语言语义。

## 2. 第一行 RMSNorm：到底归约了哪一维？

第一行平方为 [1,4,9,16]，平方均值为 30/4=7.5。gain 全为 1、eps=1e-6 时，输出等于原行除以 sqrt(7.500001)，约为 [0.36515,0.73030,1.09545,1.46059]。

这里的 mean 沿最后的 D=4 维计算，并保留长度为 1 的轴以便广播。不是对 3 个 token 求平均，也不减去行均值。若把 LayerNorm 的减均值步骤加进来，就变成另一种算子。

你可以先手算 token 2：平方均值为 2.5，正负号保留。将脚本改为打印第二、第三行，核对归约轴。

## 3. QKV 投影：一个大乘法如何等价于三个小乘法？

打包权重 Wqkv 形状为 [4,12]，由三个 [4,4] 矩阵在输出列方向拼接。Xnorm@Wqkv 输出 [1,3,12]，chunk 后三个张量都是 [1,3,4]。

参考版使用相同权重切片，分别计算 Xnorm@Wq、Xnorm@Wk、Xnorm@Wv。候选版一次算完再切分。线性代数结果等价；不同库实现的浮点累加顺序仍可能造成微小差异，所以使用容差验证。

这不是把 Q/K/V 相加，也没有把三个通道组按 token 顺序交错。若沿错误维度 chunk，shape 可能不匹配；更危险的是恰好尺寸相等时仍能跑，却改变了每个值的角色。

## 4. 拆头与转置：数据没变，谁相邻变了

[1,3,4] 先 reshape 为 [1,3,2,2]，含义是 [batch,token,head,head_dim]。再 transpose 得到 [1,2,3,2]，用于按 head 独立计算注意力。

头 0 使用原通道 0、1，头 1 使用通道 2、3。transpose 常是 stride 变化，不一定立即复制；后续 reshape 或内核可能产生必要的数据整理。不能仅从源代码没有 clone 就推断整个链没有复制。

在脚本中找到 Q 的 head 0，它是一张 3×2 矩阵：每个 token 一对数。接下来的 RoPE 正好对每一对做旋转。

## 5. RoPE：位置进入计算，但不改变这一对的长度

本例每个 head 只有两个通道，所以只有一对，频率为 1，位置 p 的角度就是 p 弧度。若某行是 [a,b]，旋转后为 [a*cos(p)-b*sin(p), a*sin(p)+b*cos(p)]。

p=0 时完全不变；p=1 和 p=2 时方向变化，但两数平方和保持。脚本检查这个不变量。真实更宽 head 会对不同通道对使用不同频率，不能把本例所有角度直接照搬。

缓存中保存已旋转 K。第 4 个 token 的位置是 3，它的 Q/K 使用角度 3；前三个 K 不再旋转。重复旋转旧 K 或把新位置归零，都是“单次调用有输出、连续生成却错误”的典型问题。

## 6. Attention：形状与 causal 语义一起检查

prefill 每个 head 的 Q/K 都是 [3,2]，Q@Kᵀ 为 [3,3]。每个分数除以 sqrt(head_dim)=sqrt(2)，然后应用可见性矩阵：

~~~text
             key 0  key 1  key 2
query 0        T      F      F
query 1        T      T      F
query 2        T      T      T
~~~

F 位置的 logits 置为负无穷，softmax 后权重为 0。每行概率和约为 1，再乘 V 得到 [3,2]。两个 head 合并回 [1,3,4]，O 投影输出形状仍为 [1,3,4]。

这也解释了为什么不允许未来 token 影响过去输出：它们必须没有进入过去 query 的归一化与加权和。只在最终输出上做 mask 已经太晚。

## 7. 两次残差和 MLP 不可少

第一次残差是原始 X 加上 Attention 的 O 投影，而不是 Xnorm 加上它。得到 R 后，第二次 RMSNorm 在 R 上运行。

gate/up 各把 D=4 投影到 F=6，两个结果逐元素做 SiLU(gate)*up，hidden 为 [1,3,6]；down 用 [6,4] 权重投回 [1,3,4]，再与 R 做第二次残差。

gate/up 的逐元素乘法不是 Attention 的矩阵乘法。确认同形后才能逐元素相乘；down 的作用则包括把宽度变回残差分支需要的 D。只因为最后 shape 相同，不代表中间可以随意交换操作顺序。

## 8. 一次 decode 为什么应当等于完整前向的最后一行？

再输入 token 3=[2,0,-1,3]。当前 Q 为 [1,2,1,2]，缓存追加后的 K/V 为 [1,2,4,2]，scores 为 [1,2,1,4]。

query 的局部下标为 0，绝对位置却是 3，因此允许访问 [T,T,T,T]。若误用局部下标生成左上三角，只能看 key 0，得到错误结果。代码显式比较绝对位置避免这个问题。

完整 causal 前向中，前三个 token 没有看过未来 token 3，所以提前计算出的 K/V 与完整计算对应部分相同。因此“前缀 cache + 一个 token”的输出应等于“一次处理四个 token”的最后一行。脚本正是比较这两条不同执行路径，而不是重复调用相同表达式做自证。

## 9. 缓存字节数只是一笔逻辑账

float64 每个数 8 字节，旧 KV 有 2×B×heads×L×head_dim=2×1×2×3×2=24 个数，占 192 字节；追加后为 32 个数，占 256 字节。

脚本打印这两项，不测进程峰值。torch.cat 期间旧 cache、新 cache、临时张量可能同时存在，因此逻辑 KV 字节不等于实际峰值内存。基准脚本在 CUDA 上才追加 allocator 峰值统计；本机 CPU 报告对未测字段保持空值。

## 本节验收与下一站

先遮住屏幕，手写 QKV、Attention、gate/up、down 的 shape，再对照脚本。然后把 heads 改为 1：head_dim 和缩放系数如何变化？把前缀长度改为 5：哪些投影权重不变，哪些中间张量增长？

最后运行 [模型主线](README.md) 的测试与测量，不要用这个小脚本的打印耗时作为性能结论。小尺寸用于看懂语义，默认尺寸用于练习采样，更大的真实工作负载还需要另外验证。
